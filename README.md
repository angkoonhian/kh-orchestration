# kh-orchestration

A Claude Code plugin that refuses any commit or merge commit whose exact tree has not passed the repository's officers (its own checks).
The files that decide what "passing" means change only with the owner's approval.
It installs a few scripts and three git hooks into a repository; nothing is bundled and nothing stays running.
It needs the kh-harness plugin, version 0.3.0 or later, installed in the same repository.
It guards against skipped steps (an agent that forgets to run the checks, or takes a one-line way round them), not against an agent set on cheating, which can run code outside the gate (see "What it does not do").
It costs about 140 ms per commit and about 8 ms per tool call.
Run its tests with `npm test` (Node 22 or later, no dependencies), and the slow ones (the real commit race, over 40 timed runs) with `npm run test:slow`.

## What it puts in your repository

`node <kh-orchestration>/scripts/apply.mjs <repository>` shows everything first and writes nothing; the owner runs it again with `--yes`, in their own terminal.

- In the working tree, to be committed: `.claude/kh-orchestration/` (the scripts and `officers.json`), `.claude/kh-orchestration.manifest.json` (the record of what was written), an entry in `.claude/kh-harness/extensions.json`, and the line `.claude/** -text` in `.gitattributes`.
- In the git directory, never committed: the `pre-commit`, `pre-merge-commit` and `reference-transaction` hooks, and the shared state in `.git/kh-orchestration/` (verdicts, approvals, exemptions, waivers, accepted records, and `bin/`, the approved copy of the scripts the hooks run).
- Refs under `refs/kh-orchestration/approved/`, one per approval, each naming the approved tree so that `git gc` and `git prune` keep it. They are not branches or tags, so an ordinary push or clone leaves them out, but `git push --mirror` and a mirror clone send them.

`node <kh-orchestration>/scripts/uninstall.mjs <repository> --yes` removes what apply wrote and kept unchanged; with `--state` it also removes the shared state and the refs under `refs/kh-orchestration/`.

## How it works

**The verdict.** `ko.mjs run` works only on a tidy tree (nothing unstaged in tracked files, no untracked file that is not ignored), and refuses while any git filter driver other than `lfs` is configured, or while any index entry is flagged assume-unchanged or skip-worktree (git does not compare such a file with the working tree, so a sparse checkout cannot produce a verdict; the refusal names the `git update-index --no-assume-unchanged` or `--no-skip-worktree` command that clears the flag). It takes the tree of the index (`git write-tree`) and its base: the merge base of `HEAD` with the base branch that `officers.json` names, or `HEAD` itself on the base branch. It runs every officer, in the listed order, on the working tree, which then equals that tree, and records a verdict keyed by the tree and the base, in the shared state: each officer's result, the first 4,000 characters of each failure's output, the waivers in force, the rules marked `approval: agent` that changed since the base, and the digest of the protected files. When the officers have finished, it checks again that the tree is tidy and that the index still holds the tree it judged; if an officer changed either (an autofixing `lint --fix`, a file written that git does not ignore, a `git add` of its own), no verdict is recorded and `run` names the changed paths: stage what is wanted, ignore or restore the rest, and run again. `verify-branch` does the same when it runs the officers. It also appends a line to the run journal (`journal.jsonl`) and, when an agent runs it in a session where kh-harness's session log is enabled, one event to that log.

An officer is a command, run without a shell from the repository's top directory, that exits 0 to pass. It sees `KO_OPTIONS` (its `options` as JSON), `KO_BASE`, `KO_TREE`, `KO_CHANGED_FILE` (a file listing the changed paths, NUL-separated) and `KO_WAIVERS`. Its time limit is `timeoutSeconds`, 600 by default and at most 3,600. An officer whose `appliesTo` globs match no changed path is recorded as skipped, which counts as a pass.

**The commit gate.** git runs `pre-commit` before a commit and `pre-merge-commit` before a merge commit; each starts `bin/gate.mjs` from the shared state, never from the tree being committed. The gate stops at the first check that decides:

1. the owner's off switch: allowed, unchecked;
2. the branch is exempt: allowed, unchecked;
3. the tree holds the install (`officers.json` and `extension.mjs` as files);
4. the working copies of `.claude/settings.json`, `.claude/kh-harness/`, `.claude/scripts/` and `.claude/kh-orchestration/scripts/` equal the tree, byte for byte and mode for mode, compared in Node, not by git;
5. `RULES.md` parses and the digest can be computed;
6. the digest is one the owner approved, and not approved before the digest of the base's tree (approvals are ordered: see the approval lock);
7. kh-harness contract 1 holds: neither settings file sets a `NODE_*`, `LD_*` or `DYLD_*` variable under `env`, `checkContract1` finds nothing in the working directory, and the probe (kh-harness's hook run on a call the extension must block) blocks it, run on a private copy of the approved tree outside the repository;
8. a passing verdict exists for this tree and base, recording the same digest;
9. the index still holds the same tree;
10. the tree is recorded for the git process that is committing, and the gate allows.

Nothing from the repository is executed before step 6 has established that the owner approved those exact bytes. A refusal prints the reason and the exact command to run next (`ko.mjs` named by its absolute path, so the line runs from wherever it is pasted), then the line `kh-orchestration: the commit gate did not allow this commit.` and one more saying to run kh-orchestration's `status` for the cause, or to ask the owner to run its `apply` (all a hook can say when `bin/` is missing or Node has moved).

**The three hooks.** `pre-commit` and `pre-merge-commit` run the gate. `reference-transaction` closes the gap between the gate's exit and git's reading of the index: in the `prepared` state of the committing process it refuses the branch update unless the new commit holds exactly the tree the gate allowed, and on an allow it records the commit as accepted (`accepted/<commit>.json`). For every other ref update (a rebase, a fetch, a reset) it exits in plain `sh` without starting Node. Each hook is a `#!/bin/sh -p` script that calls no program by name: it finds the shared state from its own path and starts Node by the absolute path recorded at install, through `env -i` with an allowlist of variables, so no `NODE_*`, `LD_*`, `DYLD_*` or shell function reaches the gate. A hook allows only when the gate exits 0 and prints the exact token `kh-orchestration: allowed`. `apply` never writes over a hook it did not write; it prints the one line to add to that hook instead.

**The approval lock.** The protected files are `docs/harness/RULES.md`, `.claude/kh-orchestration/officers.json`, `.claude/settings.json`, everything under `.claude/kh-orchestration/scripts/`, `.claude/kh-harness/` and `.claude/scripts/`, every officer script that an officer's `argv` names as a file in the tree, and every file matching a glob in `officers.json`'s `protected` list. The digest is one SHA-256 over a line `path`, `mode`, `git object id` for each of them, read from the tree object (never the working directory), with `RULES.md` contributing the hash of its canonical form. A link (symbolic or submodule) at or above anything protected makes the tree unapprovable. Approvals are a list of digests in the order given, so branches with different approved content coexist, and a verdict taken before an approval stays valid once its digest is approved. They are ordered: a tree whose protected files are an older approved version than its base's, or than the commit it is made on, is refused until the owner approves them again. Exactly: against the digest of the base's tree and that of the commit it is made on (for `verify-branch`, `HEAD`'s first parent), the tree's digest must be equal to it or last approved after it; one that is `none`, from before the install, or never approved sets no order. So `git checkout HEAD~1 -- .claude/kh-orchestration/officers.json` after a stricter officers file was approved, or a merge conflict resolved by taking the side approved earlier, needs the owner's approval again; `run`, `status` and `approve` say so, and approving again records a new approval at the end. `approve`, run by the owner in their own terminal, shows the covered files and the diff since the last approval on the branch (or, failing that, since an approved tree whose digest is the merge base's, or the most recent approved tree), asks for the word `approve`, refreshes `bin/` from the approved tree, pins that tree with a ref and records the digest. Right after `apply`, nothing is approved.

**Minor rules.** A rule in `RULES.md` with exactly one line `approval: agent` is minor: its heading's title and the values of its `why`, `verify` and `priority` lines are left out of the digest, so an agent may reword them and commit. Everything else about it is covered: its id, every other line (`status`, `enforced-by`, `pointer`, `approval`, any other key or prose), and its presence. Every change to a minor rule since the base is listed in `run`'s output, in the verdict and in `verify-branch`'s report. A rule without that line needs the owner for any change, and so does adding a rule, removing one, or marking one `approval: agent`.

**The hook extension.** kh-harness runs `.claude/kh-orchestration/scripts/extension.mjs` before every tool call of a Claude Code session, through its extension point, with `onFailure: "block"`. It is one self-contained file, starts no process and writes nothing. It blocks the one-line ways round the gate: `--no-verify` (or `-n` on `commit`) for `commit`, `merge` and `pull`; `git commit-tree`; git configuration that redirects hooks or names a command git runs; any write to the git directory (its hooks, its config, the shared state), which reading commands may still read; the owner's `ko.mjs` commands and the installer's `--yes`; unsetting the session variables those rely on; edits to the protected files other than `RULES.md` unless the owner opened the worktree for proposals with `propose`; any edit to `.claude/settings.local.json`; `git update-index --assume-unchanged` and `--skip-worktree`; and restoring or unstaging the extension's entry or its module without the other. `RULES.md` may always be edited: the digest decides at commit whether the edit was within what an agent may change.

**The session brief.** The plugin's `SessionStart` hook tells each session in a repository where kh-orchestration is installed on this machine, in under 600 characters, that commits are checked, the `run` command to use, what only the owner does, whether the worktree is open for proposals, and what is wrong when something is. It reads the state through the approved copy in the git directory, which a clone does not carry, so a clone stays silent until the owner runs `apply` there. A skill, `orchestrate`, answers the questions people ask by name ("run the checks", "is this branch ready to merge", "why was my commit refused"); nothing depends on it being used.

## Commands

The agent's commands, run with the working copy's `node .claude/kh-orchestration/scripts/ko.mjs <command>` from the repository's top directory, or by that file's absolute path from anywhere in the repository (the form the tools print):

| Command | What it does |
|---|---|
| `run` | runs the officers on the staged tree and records the verdict |
| `status [--json]` | what the commit gate sees in this worktree, with every problem and its next command; executes nothing from the repository |
| `verify-branch [--no-run]` | whether `HEAD`'s tree passes the gate's checks (an exemption or the off switch does not make it pass); runs the officers on it first unless `--no-run` |
| `unexempt <branch>` | ends a branch's exemption (it only tightens, so it is not the owner's); on a branch that does not carry the install there is no working copy, and the owner runs it from `bin/` (a session is blocked from that path), as `exempt` and `status` then print it |
| `unwaive <rule>` | ends the waiver of a rule on the current branch (it only tightens, so it is not the owner's) |

The owner's commands act only from the approved copy, `node <git-common-dir>/kh-orchestration/bin/ko.mjs <command>`, and refuse inside a Claude Code session (`CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` set):

| Command | What it does |
|---|---|
| `approve` | approves the protected files of the staged tree, after showing them and asking for the word `approve`; closes this worktree for proposals |
| `propose [--close]` | opens this worktree for agents' edits to the protected files until the next `approve`; `--close` closes it without approving. `propose` and `approve` drop the proposals of worktrees that no longer exist |
| `waive <rule> --reason <text>` | waives a rule's officer on the current branch; the officer sees it in `KO_WAIVERS` |
| `exempt <branch> --reason <text>` | lets a branch's commits through the gate unchecked |
| `off`, `on` | switches the gate off or on for the whole repository |

The plugin's commands, run from the plugin: `node <kh-orchestration>/scripts/apply.mjs <repository> [--yes] [--downgrade] [--bin-from-plugin]` (a dry run without `--yes`), `node <kh-orchestration>/scripts/detect.mjs <repository> [--json]` (a read-only report) and `node <kh-orchestration>/scripts/uninstall.mjs <repository> [--yes] [--state]`. `apply --yes` and `uninstall --yes` are the owner's and refuse inside a session. `apply` refuses where kh-harness's contract file is missing or names a contract other than 1, where kh-harness's `PreToolUse` entry script is not registered, where git is older than 2.30, where `/bin/sh` does not take `-p`, where `core.hooksPath` is set at any level, and where `.claude` is a link. When the installed `extension.mjs` was changed, `apply` keeps it, takes kh-orchestration's entry out of `extensions.json` (tool calls work; commits are refused) and prints the repair: restore the two files together from `HEAD`, then `apply --yes` again.

## What it costs

Measured on the build machine (Linux, Node 26, git 2.56, 2026-11-26):

- An allowed commit takes about 140 ms, most of it the contract probe and the second Node start, in `reference-transaction`.
- Every other ref update starts no Node, but git still starts the `reference-transaction` hook once for each state of each transaction: a rebase of 20 commits takes about 290 ms with it against about 10 ms without it.
- The hook extension: about 7 to 11 ms on each tool call (kh-harness's extension loader and this module), well inside kh-harness's latency budget. Measured as `stage1-measures.test.mjs` does: kh-harness's registered `PreToolUse` entry script timed in one repository without and with the extension, the fastest of 20 runs each against as many bare Node starts.
- `approve`: about 160 ms, of which the check that the new `bin/` loads is three Node starts. `run`: one Node start plus the officers' own time.
- With kh-harness's session log enabled, each `run` an agent starts in a session adds one event. The gate's probe runs kh-harness's hook in a private copy outside the repository, for which the log is not enabled, so commits add nothing to it.

## What it does not do

**The shared state is not tamper-proof.** Verdicts and approvals are files in the git directory. The extension blocks a session's one-line writes to them, and the run journal keeps a record, but code an agent manages to run outside the gate (a script it wrote to disk, a command git runs from configuration before the hook) can write a false verdict or approval. This guards against skipped steps, not against an agent set on cheating. When it matters, `verify-branch` (without `--no-run`) runs the officers again on the branch's head.

**What the order of approvals does not catch.** Two cases remain. (a) On the base branch, a commit git never hooks (`git revert`, `git reset --hard`) moves the point the order is measured from: after a revert of a commit that tightened the checks, `verify-branch` fails, but one gated commit on top of it is accepted and clears that. The owner should treat a revert of a commit that changed the checks as a change to approve. (b) "Approved later" does not mean "holds the base's change": a stale branch whose change to the protected files was approved after the base tightened its checks can replace the base's stricter checks through a merge that takes the branch's side. When approving a change to the checks on a branch, merge the base branch into it first.

**Who a command runs as.** `ko.mjs`, the officers and everything they start run as whoever types the command, with that person's environment and rights. The working copy's scripts are the session's to change until the next commit refuses them, so the owner runs the pre-merge `verify-branch` from the approved copy, `node <git-common-dir>/kh-orchestration/bin/ko.mjs verify-branch`, not from the working copy (`docs/ROLLOUT-vyugate.md` does so). Run it ON THE BRANCH, before merging: on the base branch afterwards it judges only the last commit against its parent. The plugin's own checkout, from which `apply` and the session brief run, is not protected: keep it where sessions do not work, or read-only. The extension judges Bash and the edit tools (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`); a writing tool of another kind (an MCP filesystem tool, say) is not judged at all, and the digest and the gate are then the only check. The gate's private copy of the approved tree sits in a temporary directory the same user can write; a process rewriting it during the probe can change what the probe runs, but not that commit's outcome, which was read first.

**What the hook extension does not catch.** It reads a command's words; it is not a shell. It does not see: `eval`, and variables holding paths or flags (`git merge $F`; `N=-n; git commit --trailer -m "$N"`); a script written to disk and then run; strings built up inside inline code; an encoded payload piped to an interpreter (`… | base64 -d | sh`), `sed -f` and `awk -f` script files; editor scripting (`vim -es`, `ed`, `ex`) and `tar --checkpoint-action`; git options that run a command (`rebase -x`, `bisect run`, `submodule foreach`), a pager or editor git starts, and an alias already configured; a copy of `ko.mjs` under another name, or its name or subcommand produced by a search or a substitution; a glob or a search whose output becomes another command's words; copying or unpacking over the git directory through its parent, or through a link made earlier; variables that git or a shell runs, or that steer git, when exported in an earlier command line; a shell write to a tracked protected file such as `officers.json` (only the edit tools are guarded; the digest refuses the commit); `.claude/settings.local.json` changed through the shell (the gate's contract check refuses the commit); and, while `officers.json` cannot be read, edits to the officer scripts and `protected` files. Keeping the extension's entry and its module together is best effort: pathspec magic, globs, absolute paths, `git -C` or `git stash push -- <one of them>` can still split them, after which kh-harness blocks every tool call until the owner runs `apply --yes`. That writes the pair back; when the module itself was changed, it keeps the module, takes the entry out so that tool calls work, and prints the rest of the repair: restore both files from `HEAD` together, then `apply --yes` again (`docs/ROLLOUT-vyugate.md`, step 12). A commit made outside Claude Code is not seen by the extension at all, so `--no-verify` typed by a person still skips `pre-commit` and `pre-merge-commit`. The full list is the header of `assets/scripts/extension.mjs`.

**Commits git never hooks.** git runs no commit hook for a rebase, a cherry-pick, a revert, `git am`, a fast-forward merge, `git stash`, `update-ref` and other plumbing, or a commit pulled from a clone. These are not blocked, since agents need them. Their result has no verdict for its tree, and `verify-branch` says so and fails until the officers pass on the head; `status` names such a head too. Run `verify-branch` before every merge into the base branch. Where the `reference-transaction` hook could not be installed (an existing hook of the owner's that does not host kh-orchestration's line), a change to the index in the instant after the gate allowed a commit is not caught; `verify-branch` and `status` report the missing hook, and `verify-branch` is the remedy. A clone of an installed repository has no hooks and no shared state (they live in the git directory) until the owner runs `apply --yes` in it, so commits there are not checked.

**What a verdict does not lock.** The digest covers the protected files only. It does not cover the code an officer checks (by design), the tools an officer starts (`node_modules`, `npm`, `python3` and anything found through `PATH`), a directory named in `argv` (`eslint src`), `package.json` for an `npm run` officer unless `package.json` is added to `protected`, or anything else not in `protected`. `apply` and `detect` say per officer what the digest covers. An officer inherits the environment of whoever runs `run` (`NODE_OPTIONS`, `PYTHONPATH` and the like). An officer whose `appliesTo` matched nothing counts as a pass. A verdict is about the working directory at the moment the officers ran, not about a clean checkout of the tree: ignored files the officers read (a source file caught by a broad `.gitignore` pattern, a `.env`, build output) count in it though no commit holds them. A file an officer changes and puts back while it runs is not seen. A flaky officer can be run again until it passes, and the verdict records only the last run.

**Known over-blocks an agent will meet.** Each has a plain way round:

- inline code that mentions a guarded word (`node -e "…git commit -n…"`) and a test-name pattern behind a runner (`npx jest -t 'commit -n'`, `vitest -t`, `rspec -e`): put the code in a file, or the pattern in the test's configuration;
- `git commit --author "$A"`: write the value out, or glue it (`--author="$A"`);
- a `PATH=` or `HOME=` assignment on any command in a line that also runs git: run git in a line of its own;
- `ssh host git commit -n …`: run the remote command from the person's terminal;
- `git config --remove-section filter.lfs` and other writes of hook-related configuration: the owner changes configuration;
- `rm .git/index.lock` without `-f` and any other write into the git directory: `rm -f .git/index.lock` is the one write allowed;
- unstaging `extensions.json` or `extension.mjs` alone: unstage the whole install, as the message says;
- a commit while the install's live files differ from the tree: stage them for approval, or have the owner run `apply --yes`;
- `run` refuses while a git filter driver other than `lfs` is configured.

**Platform notes.** It needs git 2.30 or later and a `/bin/sh` that accepts `-p` (`apply` checks both). The hooks have been tested with `/bin/sh` as bash and as zsh in `sh` emulation, not dash, BusyBox or ksh. A repository whose `.claude` is a link cannot install it. The hooks name Node by its absolute path, so after Node moves (an nvm switch, an upgrade to another path) every commit is refused until the owner runs `apply --yes` again. A `core.hooksPath` set at any level, the global one included, makes git skip the repository's hooks, which turns the gate off: `apply` refuses while one is set (the hooks must live in the git directory's own `hooks/`, since their path is how they find the shared state, so a repository that manages its hooks through `core.hooksPath`, with husky or the like, cannot install kh-orchestration), and `status` and the session brief report one set later (one set in another worktree's own configuration is seen only by `status` there). A later line in `.gitattributes` that overrides `.claude/** -text` is not detected. Refs under `refs/kh-orchestration/approved/` accumulate, one per distinct approved digest, and the `accepted/` records one per gated commit. Two owner commands run at the same moment can lose one update. `uninstall` leaves the commits that already contain the install as they are, and does not remove a hooks folder that `apply` created.

**What an agent may change in a minor rule.** The heading's title and the values of `why`, `verify` and `priority` (so an agent may change a minor rule's check command and move it between `normal` and `high`), and nothing else. Those parts may not contain `<!--`, `-->`, a control character other than TAB, a line or paragraph separator, or a zero-width or bidi character; such a rule makes the tree unapprovable. A free part inside a closed HTML comment is covered byte for byte.
